# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PakCyberbot Life Manager — a local-first, cross-platform personal life management app: goals (with tasks built in), calendar, a Time Table weekly routine, personal savings, a book/video/web-link library, life quotes, Google Drive sync, an AI-powered News digest, Entertainment "worth it" verdicts, Earning Ways ideas/guides, a Jobs aggregator, a Health section, and an optional File Manager. The primary target is desktop (Electron); a Capacitor/Android mobile companion (`apps/mobile`) is in progress (Phase 1: read-mostly UI + its own local data — see the Mobile app section below) — no iOS target, since building one needs a Mac. The full product vision, module roadmap, and design rationale live in [structure.md](structure.md) (technical) and [framework.md](framework.md) (the user's personal methodology/values — several AI features actually read from this file at runtime, not just aspirationally). Read those before making roadmap-level decisions; this file is about the code, not the plan.

## Commands

Run everything from the repo root (npm workspaces — no pnpm/yarn).

- `npm install` — installs all workspace packages at once.
- `npm run dev` — starts the desktop app (electron-vite dev server + Electron), with renderer hot reload. Main-process/preload changes need the command restarted.
- `npm run typecheck` — `tsc --noEmit` across the whole workspace via `apps/desktop/tsconfig.json` (which includes all `packages/*/src`). Run this after any change — there's no separate lint step and no test suite yet.
- `npm run build` — `electron-vite build` (produces `apps/desktop/out/{main,preload,renderer}`; no installer/packaging step configured yet — that would be a separate `electron-builder` addition).
- `npm run mobile:dev` / `npm run mobile:build` — plain Vite dev server / production build for `apps/mobile` (browser-only, no native shell — useful for fast UI iteration, but `window.api` won't exist so any screen will throw on first store call; real testing needs the steps below).
- `npm run mobile:sync` — builds `apps/mobile` then `cap sync android`, copying the web build + native plugins into `apps/mobile/android`. `npm run mobile:run` does that and then `cap run android` (needs an emulator/device already running). See the Mobile app section for the full first-time setup and known local-environment gotchas (Gradle/JDK TLS trust).

**Gotcha**: if `ELECTRON_RUN_AS_NODE=1` is set in the shell (happened during development in this environment, common when the shell is itself hosted by an Electron-based tool), `npm run dev` launches but crashes with `Cannot read properties of undefined (reading 'whenReady')` — `electron.exe` runs as a plain Node process instead of the real Electron runtime. Fix: `env -u ELECTRON_RUN_AS_NODE npm run dev` (bash), or unset it before running.

## Architecture

### Monorepo layout

npm workspaces, 4 packages + 2 apps, all TypeScript, no build step for internal packages — Vite/esbuild compile each package's `.ts` source directly wherever it's imported (`package.json` "main"/"types" point straight at `src/index.ts`).

- **packages/shared** — types + tiny utils (id/date/currency helpers). Zero dependencies, so it's importable from any target (desktop, mobile) unchanged.
- **packages/db** — SQLite schema (`schema.ts`, shared verbatim by both drivers) + the `DataStore` abstraction (`DataStore.ts`) + two concrete implementations: `electronDriver.ts` (sql.js, desktop) and `capacitorDriver.ts` (`@capacitor-community/sqlite`, mobile). **Neither driver is re-exported from `packages/db/src/index.ts`** — each app imports its own driver via a deep path (`@life-manager/db/src/electronDriver` / `@life-manager/db/src/capacitorDriver`) so the other platform's dependencies (sql.js + `node:fs`/`node:path` vs. `@capacitor-community/sqlite`) never end up in the wrong app's typecheck scope or bundle. Each app's `tsconfig.json` mirrors this: its `include` lists the specific `packages/db/src/*.ts` files it actually uses, not the whole directory.
- **packages/core** — Zustand stores (one per module) that call a generic `api.db.{list,get,create,update,remove}` shape (`api.ts`) exposed on `window.api`. Stores never talk to Electron/IPC or Capacitor plugins directly — that seam is exactly what lets the same store code run unmodified on both apps; only what implements `window.api` differs (desktop: `electron/preload.ts` over IPC; mobile: `apps/mobile/src/api/mobileApi.ts` calling Capacitor plugins/`fetch` directly in the same JS context).
- **packages/ui** — all React screens/components/theme for **desktop**. `apps/desktop` mounts `<App/>` from here. A handful of platform-neutral pieces (`ThemeProvider`, `ThemeToggle`, `TimeTableClock`, `renderPdfCoverFromBase64`, and the base `Card`/`Badge`/`Button`/`Dialog`/`EmptyState`/`ProgressBar`/form-control components) are also exported from `packages/ui/src/index.ts` specifically so `apps/mobile` can reuse them — mobile does **not** reuse desktop's screens (see the Mobile app section: different interaction model, different nav, not a replica).
- **apps/desktop** — the primary, shipped app target. Electron main process (`electron/main.ts`), preload (`electron/preload.ts`), Drive sync logic (`electron/driveSync.ts`), AI features (`electron/ai/`), and the Vite renderer entry (`src/main.tsx` + `index.html`).
- **apps/mobile** — Capacitor/Android companion, Phase 1 in progress. See the Mobile app section below.

### Why sql.js instead of better-sqlite3

`better-sqlite3` needs native compilation rebuilt against Electron's ABI (node-gyp/MSBuild), which is known to break on Windows paths containing spaces/apostrophes — this repo's own folder path has one, and it did break during development. sql.js (SQLite compiled to WebAssembly) needs zero native compilation. Trade-off: the whole DB lives in memory; `electronDriver.ts` exports it to disk (debounced ~250ms) after every write, and flushes synchronously on quit. Fine at personal-app data volumes.

### Generic CRUD over IPC, not per-entity handlers

Every table (goals, tasks, events, accounts, transactions, budgets, books, videos, webLinks, quotes, newsCategories, newsItems, entertainment, earningWays, jobSearches, jobListings, fileCategories, fileLinks, daySchedules, timeSlots, links, exercises, doctorAppointments, foods, bodyMetrics, savingsEntries, wishlistItems) goes through the same 5 IPC channels (`db:list/get/create/update/remove`) and the same `DataStore` methods — adding a new module's table almost never needs new IPC plumbing, just: a `CREATE TABLE` in `schema.ts` (columns matching the TS type's camelCase field names exactly — no snake_case mapping layer), a shared type in `packages/shared`, a Zustand store in `packages/core`, and a screen in `packages/ui`. `newsItems`/`jobListings` are the exceptions that bypass soft-delete (see `ElectronDataStore.replaceNewsItems`/`replaceJobListings` — hard-deleted and reinserted per category/search on refresh, since they're live digests, not history worth keeping). A 6th channel, `db:hardRemove` (→ `ElectronDataStore.hardRemove`, a genuine `DELETE FROM`), exists specifically for Library's `removeBook`/`removeVideo`/`removeWebLink` (and blog-type `removeCategory` in News) — no "undo" value in a deleted row, and each can carry a sizable `data:` URI image that shouldn't linger in the DB.

**Column migrations**: `CREATE TABLE IF NOT EXISTS` only covers a table that doesn't exist yet — a column added to a table that already shipped (e.g. `Exercise.videoUrl`, `Task.linkType`, `Book.category`) needs an explicit `ALTER TABLE` for anyone who already has that table on disk. There's no formal migration system; `electronDriver.ts`'s `ensureColumn(table, column, definition)` is the ad hoc equivalent — checks `PRAGMA table_info` first so it's idempotent, called once per new column right after `SCHEMA_STATEMENTS` run. Add both: the column in `schema.ts`'s `CREATE TABLE` (for fresh installs) *and* an `ensureColumn` call (for everyone else) — the second one gets easy to forget since fresh installs work fine without it.

`settings` is the one table with its own dedicated `getSetting`/`setSetting` methods (keyed by `key`, not `id`) — used for the PDF reader path/type, Google OAuth credentials/tokens, the active AI provider + its API keys, the default currency, and per-feature AI prompt overrides (`entertainmentPrompt`). Any key in `SECRET_SETTING_KEYS` (`packages/db/src/secretCrypto.ts`) is transparently AES-256-GCM-encrypted on write and decrypted on read — currently: `googleClientId`, `googleClientSecret`, `googleRefreshToken`, `geminiApiKey`, `openaiApiKey`, `anthropicApiKey`. Add a new credential-holding setting key to that `Set` and it's covered automatically; forgetting to would store it in plaintext.

### electron-vite build gotchas (`apps/desktop/electron.vite.config.ts`)

- electron-vite's dev runner always expects `out/main/index.js` and `out/preload/index.js` — since the entry files here are named `main.ts`/`preload.ts` (not `index.ts`), `output.entryFileNames` is forced to `'index.js'` in the config for both builds.
- `externalizeDepsPlugin` only reads `apps/desktop/package.json`'s own `dependencies` to decide what to leave un-bundled (vs. transpiled inline) for the main/preload builds. A runtime dependency declared only in a workspace package (`sql.js` lives in `packages/db`'s `package.json`) won't be recognized and gets bundled incorrectly, breaking at runtime — it has to also be listed in `apps/desktop/package.json`. Workspace packages themselves (`@life-manager/*`) are explicitly excluded from externalization (see `workspacePackages` in the config) so their TS source gets bundled/transpiled rather than left as an unusable `require()` of `.ts` files.

### Packaging a real installer (`npm run dist`, `apps/desktop/package.json`'s `"build"` field)

`electron-builder` (config lives directly in `package.json`, not a separate `electron-builder.yml`) produces a Windows NSIS installer at `apps/desktop/release/PakCyberbot-Life-Manager-Setup-<version>.exe` — `electron-vite build` runs first, then `electron-builder --win` packages `out/` into `release/`. Two gotchas hit and fixed while first setting this up, both confirmed by actually launching the packaged `.exe` (not just checking the build logs — the build itself succeeds either way; only running the real output catches these):

- **`electronVersion` must be pinned.** The project's own `electron` dependency is a range (`^31.0.0`, so `npm install` can pick up patch releases) — electron-builder refuses to resolve a version range on its own (it needs an exact version to download the matching platform binaries) and fails immediately with "Electron version is a range, not a fixed version." Fixed by setting `"electronVersion"` explicitly in the build config to whatever's actually installed (`node -e "console.log(require('electron/package.json').version)"`) — this has to be bumped by hand if the installed Electron version changes, since nothing keeps it in sync automatically.
- **The window icon needs `extraResources`, the same way `framework.md` does (see `ai/framework.ts` / `resolveIconPath()` in `main.ts`).** `main.ts` computed the icon path as `path.join(__dirname, '../../resources/icon.ico')`, which resolves to a real file only in dev — packaged, `__dirname` is a *virtual* path inside `app.asar`, and that same relative traversal lands on a path that's still inside the asar's virtual namespace (nothing copies `resources/` into the asar by default; the build's `files` list is intentionally just `out/**/*`). Confirmed live: the packaged app launched fine but logged `Failed to load image from path ...app.asar\resources\icon.ico`, and the window had no icon. Fixed the same way as `framework.md`: an `extraResources` entry copies the real `resources/icon.ico` to `process.resourcesPath/resources/icon.ico` (a real file next to `app.asar`, not inside it), and `resolveIconPath()` tries that packaged location first, falling back to the dev-relative path. Any *new* file main.ts needs to read at a real filesystem path (not just `require`-bundled code, which Vite already inlines) — an icon, a template, anything — needs this same extraResources + dual-path-resolution treatment, or it'll silently work in dev and silently fail once packaged.

Not yet done: code signing (the installer is unsigned — Windows SmartScreen will warn "unknown publisher" on first run; there's no code-signing certificate for this project), a macOS/Linux target (`win` only currently, matching "desktop-only, Windows-developed" reality), and auto-update (no `publish` config — every new version is a manual download/reinstall for now).

### In-app PDF viewer + automatic bookmark (`apps/desktop/electron/main.ts`)

Books open in a dedicated `BrowserWindow` using Chromium's own built-in PDF viewer (`webPreferences.plugins: true`), not an external reader — deliberate, since neither Adobe nor Foxit expose any API to ask "what page is the user on," so automatic bookmark tracking is only possible for a viewer this app controls. The viewer updates its window URL as `#page=N` while scrolling; `did-navigate-in-page` on that window's `webContents` catches it (`parsePageFromUrl`), and on window close the last-seen page is written to the book's `bookmarkPage` and pushed to the renderer via the `book:bookmarkUpdated` IPC event (see `useBooksStore.subscribeToBookmarkUpdates`). A separate "open externally" path (configured Adobe/Foxit, or the OS default via a `file://…#page=N` URL) exists but can't auto-track — there's no way to observe another process's reading position.

### Google Drive sync (`apps/desktop/electron/driveSync.ts`)

Plain `fetch` calls against the Drive v3 REST API and Google's OAuth token endpoint — not the `googleapis` SDK, which is tens of MB for the handful of calls this needs. Uses the `drive.file` scope only (app can see only what it creates — avoids Google's sensitive-scope verification process). Auth is the installed-app OAuth loopback flow (RFC 8252): a temporary `127.0.0.1` HTTP server catches Google's redirect after consent in the system browser. Requires the user's own Google Cloud OAuth "Desktop app" Client ID/Secret, pasted into Settings — there's no way to provision that on their behalf. Push finds-or-creates a "PakCyberbot Life Manager" Drive folder and uploads/overwrites `life-manager.sqlite` in it; pull downloads and overwrites the local file, then the whole app relaunches (`app.relaunch()` + `app.exit()`, which skips the normal quit-flush) rather than trying to hot-reload the in-memory sql.js DB and every renderer store individually.

**Two real bugs found via live OAuth testing, both fixed** (the failure mode in each case looked like success — the browser showed the right page — while the actual connection silently failed, so neither would have been caught by just reading the code):
- **The token exchange sent a mismatched `redirect_uri`.** The original code called `server.close()` and only *then* read `server.address()` to build the `redirect_uri` for the token-exchange POST — but Node nulls the server's internal handle synchronously inside `close()`, so `address()` returns `null` immediately after (confirmed with a 3-line standalone script), silently falling back to port `0` (`http://127.0.0.1:0/`). That never matches the `redirect_uri` Google issued the authorization code for, so the exchange was rejected — but only *after* the loopback server had already responded "Connected — you can close this tab," so the browser-side symptom looked identical to success. Fixed by capturing `redirectUri` once, in an outer-scoped variable, when the server starts listening — the same value is then reused for both the initial authorization URL and the later token exchange, never recomputed after `close()`.
- **`drive.file` needs registering on the OAuth consent screen itself, not just requested in the auth URL.** Even with the redirect fixed, Push/Pull can still fail with `403 insufficient authentication scopes` if the scope was requested in the authorization URL (`SCOPES` constant) but never added under Cloud Console → OAuth consent screen → Scopes — Google silently drops an unregistered scope from what it actually grants rather than erroring at consent time. A stale refresh token from before the scope was registered won't pick it up either — refreshing a token can never grant it a *new* scope, only a fresh consent screen visit can, so reconnecting (Disconnect then Connect again) is required after fixing the consent screen config.

### Local backup (`db:export`/`db:import` in `main.ts`)

A Google-free alternative next to Drive sync, same relaunch-on-import reasoning. Export calls `store.flush()` — a new `ElectronDataStore` method distinct from `close()` (which also shuts the store down) — before `fs.copyFileSync`, so the exported copy reflects the true latest state rather than whatever the debounced autosave last wrote. Import validates the picked file starts with SQLite's 16-byte magic header (`"SQLite format 3\0"`, literally a null byte, not a space or other whitespace — verified against a real DB file's actual bytes during the build rather than assumed, since it's an easy thing to get subtly wrong) before overwriting anything, then follows the identical `app.relaunch()` + `app.exit()` pattern as Drive's pull.

### Multi-provider AI (`apps/desktop/electron/ai/`)

Every AI feature goes through `callAI(provider, apiKey, prompt) -> string | null` in `providers.ts`, which dispatches to Gemini/OpenAI/Anthropic's plain REST APIs (no SDKs) and always returns raw text or `null` on any failure — callers degrade gracefully, never throw. The active provider + its key live in settings (`aiProvider`, `{provider}ApiKey`). Model names are pinned constants that **will** go stale — this happened for real mid-build: a live call to `gemini-2.5-flash` came back `404`, with the API itself naming `gemini-3.6-flash` as the replacement. If a provider starts failing, check the model constant first.

Deliberately API-key-only for all three providers — there is no supported way for a third-party app to authenticate against a ChatGPT Plus or Claude Pro/Max *subscription* (separate from their APIs by design on both platforms), and faking it via web-session scraping would violate ToS. Don't build that if asked; explain why instead.

Two shared helper patterns worth knowing before touching any AI feature:
- **`framework.ts`** — `readFrameworkFile()` / `extractFrameworkSection()` read `framework.md` off disk (repo root, resolved relative to the bundled `out/main/index.js`) and pull out one `## N. Heading` section by regex. Used by both `entertainment.ts` (§6) and `earningWays.ts` (§1 + §5). Falls back to no context (not an error) if the file isn't found.
- **Never ask the AI for a URL.** Every feature that needs real links either sources them from a non-AI channel (News & Updates uses Google News RSS, matched back to AI-written summaries **by list index**, never by asking the AI to reproduce a title/URL) or asks for resource **names** only (Earning Ways guides). This was a deliberate lesson from building News & Updates — see below. Entertainment's poster/thumbnail lookup follows the same discipline for images: a real Wikipedia search by title, never an AI-guessed image URL.

### AI provider status (`apps/desktop/electron/ai/health.ts`)

None of the three providers expose a real remaining-credits/quota number for free/pay-as-you-go tiers, so there's no honest way to show a literal "credits" figure. `checkAiHealth(provider, apiKey)` makes a real, minimal completion request through the exact same `callAI()` path every AI feature uses, and classifies the outcome: `rateLimited: true` for a 429 or an error body containing "quota"/"RESOURCE_EXHAUSTED"/"rate limit", vs. a general failure for anything else (bad key, network). **Deliberately not** a cheaper `GET /models`-style metadata check — that was the first implementation, and it was wrong: live-tested against a Gemini key with its real `generateContent` quota exhausted (429 confirmed via an actual Entertainment-verdict call), `GET /models` still returned 200, because Gemini meters generation and metadata calls on separate quotas. A real completion costs a sliver of quota to check, but a metadata check reporting "OK" for a provider that can't actually generate anything is worse than not checking at all. Two update paths converge on the same `lastAiStatus` in `main.ts`: an explicit `ai:checkStatus` call (Settings' "Check now"), and an ambient one — `providers.ts` now records the HTTP status/body of each provider call's *last failure* in a module-level `lastError` (cleared on success, read via `getLastAiError()`), and every existing AI-feature IPC handler calls `syncAiStatusFromLastCall(provider)` right after its `callAI`-based call completes, so a quota failure surfaces the moment it happens rather than only when someone manually checks. Status changes push to the renderer via `ai:statusChanged` (same pattern as `book:bookmarkUpdated`), consumed by `useAiStatusStore` so Settings' status panel and the Sidebar's warning banner (shown only when not-OK) stay in sync without polling.

### News & Updates (`apps/desktop/electron/ai/news.ts`)

Real articles from Google News RSS (`news.google.com/rss/search?q=…`, free/keyless/no billing) + the configured AI provider ranking/summarizing them. **Not** built on Gemini's "Google Search grounding" tool, despite that being the obvious way to get an LLM to cite sources — live-tested during development and found to need a billing-enabled Google Cloud project even on an otherwise free-tier key (`429 "check your plan and billing"`, specific to that tool). `newsCategories` holds one editable custom category plus three fixed types (`global-politics`/`country`/`city`, the latter two needing a `locationValue`); `buildNewsQuery()` in `main.ts` maps a category to an RSS query + AI framing string.

A 5th category type, `blog`, is different in kind from the other four: instead of an RSS+AI digest, the user pastes a blog/news site's URL and gets a live, scrollable, in-app view of the real page — for a quick skim, not a summary. Embedding it inline via `<iframe>`/`<webview>` isn't viable: this app's CSP (`apps/desktop/index.html`) has no `frame-src` (falls back to `default-src 'self'`, blocking any iframe outright), and even without that, most real news/blog sites set `X-Frame-Options`/`frame-ancestors` and would refuse to be framed anyway. The working approach — `openWebsitePreviewWindow()` in `main.ts`, IPC `system:openWebsite` — is the same trick as the PDF reader below: a plain child `BrowserWindow` doing a real top-level `loadURL()`, which is neither "framing" nor subject to either restriction. `news:fetch`'s handler branches on `category.type === 'blog'` *before* the RSS/AI path — instead of `buildNewsQuery`, it calls the shared `fetchWebPreview(url)` helper (see Library below) and stores the result on the category row itself (`url`/`previewImage`/`previewFavicon` columns), returning `{ items: [] }` so the existing Refresh-button/loading UX in `useNewsStore` needs no special-casing for this type. Blog categories are hard-deleted on remove (`useNewsStore.removeCategory`), not soft-deleted like every other category type — they carry an inlined `data:` preview image, same cleanup reasoning as Library books/videos below.

### Library — Web Links (`packages/ui/src/screens/LibraryScreen.tsx`, a 3rd tab alongside Books/Videos)

Save an article/page URL to explore later; a preview thumbnail is fetched automatically, same fetch-in-main-inline-as-`data:`-URI convention as every other thumbnail in this app. The fetch itself — `fetchWebPreview(url)` in `main.ts`, IPC `media:fetchWebPreview` — is shared with News & Updates' `blog` category type above: no HTML-parser dependency, just regex extraction of `og:title`/`og:image`/`<link rel="icon">` (falling back to `/favicon.ico`) from the page's own HTML, consistent with how `ai/news.ts` already regex-parses RSS XML rather than pulling in a full parser for a handful of tags. A realistic desktop-browser `User-Agent` header is set, since a lot of sites silently reject or serve a stripped page to Node's default fetch UA. `useWebLinksStore.addWebLink()` follows Entertainment's async-enrichment pattern (create the row immediately, patch in the preview once the fetch resolves) rather than Video's blocking-`await`-before-create style. Deletes go through `hardRemove`, same reasoning as books/videos: the row carries a sizable inlined preview image, no recovery value in keeping it around.

### Entertainment verdicts (`apps/desktop/electron/ai/entertainment.ts`)

On `addItem`, the row is created immediately (`considering` status, verdict fields null) and the AI verdict fills in asynchronously — same non-blocking pattern as Library's cover/thumbnail fetch. One JSON call returns verdict/reasoning/skillsImproved/benefits/timeCostEstimate/addictiveness/mentalEffects together. Grounded in `framework.md` §6 **and** a Settings-editable `entertainmentPrompt` — both get folded into the same prompt when present.

### Earning Ways (`apps/desktop/electron/ai/earningWays.ts`)

Two independent AI calls: `suggestEarningWays()` (reads active Goal titles + `framework.md` §1/§5, returns up to 6 ideas the user explicitly opts into adding — never auto-inserted) and `generateEarningWayGuide()` (on-demand, first detail-dialog open, cached in the row after — `guideOverview` etc. columns — until "Regenerate").

### Jobs (`apps/desktop/electron/ai/jobs.ts`)

Same News & Updates shape, applied to job listings: real data from four free, keyless sources (RemoteOK, Arbeitnow, We Work Remotely RSS, Jobicy — deliberately not LinkedIn/Indeed/Glassdoor, whose ToS explicitly forbid scraping) queried in parallel via `Promise.allSettled`, normalized, deduped by URL, then optionally ranked/annotated by the AI provider using the same index-based reference pattern as News (never asked to reproduce a title/URL itself). `jobSearches` (label, comma-separated keywords, an AI framing prompt) are managed entirely from Settings — the Jobs screen only displays + refreshes, no criteria live outside Settings. If adding a fifth source, follow the existing `fetchX(keywords): Promise<RawJob[]>` shape and add it to the `Promise.allSettled` array in `fetchJobsForSearch` — one failing source must never sink the others.

### Sections — per-module show/hide (`packages/shared`'s `TOGGLEABLE_SECTIONS`)

Started as a File-Manager-only `fileManagerEnabled` boolean, then generalized on request into a mechanism every module uses. `TOGGLEABLE_SECTIONS`/`ToggleableSectionId` live in `packages/shared` (not `packages/ui`, even though it's primarily a navigation concern) specifically so `packages/core`'s `useSettingsStore` can reference the same list without depending on `packages/ui` — the dependency direction in this monorepo is always shared → core → ui, never the reverse. `ScreenId` in `packages/ui/src/navigation.ts` is `'dashboard' | ToggleableSectionId | 'settings'`, deriving from the shared list rather than duplicating it.

Storage: one `disabledSections` setting, comma-separated ids that are *off* (everything absent from it defaults to on) — `useSettingsStore.setSectionEnabled()` reads/writes it. `Sidebar.tsx` filters `NAV_ITEMS` by `enabledSections[item.id] !== false` (note: `!== false`, not `=== true` — `dashboard` isn't a key in the map at all and must still pass). `App.tsx` watches `enabledSections` and bounces to Dashboard if the currently-active screen becomes disabled out from under it.

**Adding a new toggleable module**: add its id to `TOGGLEABLE_SECTIONS` in `packages/shared`, an entry to `SECTION_META` in `SettingsScreen.tsx` (label + icon for the toggle list), and a `NAV_ITEMS` entry in `Sidebar.tsx` — three edits, no new settings key.

### File Manager — hostname-gated folder/file links

`fileCategories` is self-referencing via `parentId` for nesting; deleting a category cascades to every descendant category and every link inside any of them (`collectDescendantIds` in `useFileManagerStore.ts` — a plain BFS over `parentId`, unit-tested separately from Electron during the build since it's pure logic). Each `fileLinks` row records the hostname it was added from; `openLink()` in the store checks that against the current machine **before ever calling out to the main process** — a mismatch is a pure no-op in the renderer, not an IPC call that fails. Two new main-process capabilities exist only for this feature: `dialog:pickFileOrFolder` and `system:openLocalPath` (wraps `shell.openPath`, which transparently handles both a folder and a file).

**`dialog:pickFileOrFolder` takes an explicit `kind: 'file' | 'folder'`, not a combined dialog.** The original version passed `properties: ['openFile', 'openDirectory']` together to `dialog.showOpenDialog`, on the assumption (stated in the code's own comment, and wrong) that Windows/Linux support combining them as a toggle. Electron's actual documented behavior is the opposite: **on Windows and Linux, combining those two properties silently collapses to a directory-only picker** — file selection never worked on this platform, only macOS handles the combination as a real toggle. Found by reading the installed `electron.d.ts` directly rather than trusting the old comment. Fixed by requesting only the matching single property per `kind`; every call site (File Manager's `NewLinkDialog`, the Goals task-link dialog) now shows separate "Browse file"/"Browse folder" buttons instead of one relying on the broken combined mode.

### Time Table — weekly routine, not Calendar's dated events

`daySchedules` is a fixed set of exactly 7 rows (`dayOfWeek` 0=Sun..6=Sat), seeded once and **only ever updated** from the UI — `useTimeTableStore.updateSchedule()` looks up the existing row by `dayOfWeek` and calls `db.update`, never `db.create`/`db.remove` for this table. `timeSlots` are the actual free-form content, also keyed by `dayOfWeek` (not a date) so they repeat every week. `minutesBetween`/`formatMinutes` (`packages/shared`) handle the wake→sleep and slot-duration math, including the overnight-wrap case (sleep time numerically earlier than wake time) — this and the full seed/CRUD flow were verified with direct store calls before shipping, since none of it touches a native dialog and so, unlike File Manager/Backup, it's fully testable without a human clicking through anything.

Slots are editable (`SlotDialog` — the same add-dialog component reused in edit mode, matching `TaskDialog`'s pattern) and clonable to other days (`cloneSlotToDays(slotId, days)` — copies one slot's time/label/notes/color onto the same day-of-week rows via `addSlot`, the per-slot analogue to `applyScheduleToDays`'s whole-day wake/sleep copy).

**Clock view** (`packages/ui/src/components/timetable/ClockView.tsx`), toggled alongside the plain list: two inline-SVG 12-hour analog clock faces (AM/PM) drawing each slot as a colored ring arc — a real clock rather than a bar, per an explicit ask for something more creative. `splitIntoClockSegments(startDec, endDecRaw)` is the load-bearing function: it clips a `[start, end)` range (in decimal hours, `end` possibly > 24 for an overnight wrap already normalized by the caller) against three windows — `[0,12)` AM, `[12,24)` PM, and `[24,36)`, which maps back onto the *same* AM face — so a slot like sleep `23:00`–`07:00` correctly renders as a PM arc `330°→360°` plus an AM arc `0°→210°`, rather than only showing the PM half. `describeArc` (polar-to-Cartesian, `A` command) special-cases a would-be full 360° sweep by splitting it into two 180° arcs, since a literal 0°→360° path in SVG degenerates to a single point. No test suite exists to catch a math mistake here, so all of this was verified against 6 cases (plain AM slot, plain PM slot, one spanning the AM/PM boundary, the overnight-wrap sleep case, and both full-AM/full-PM day-length arcs) via a standalone Node script reimplementing the same formulas before wiring them into the component — same discipline as the SQLite header check and the Wikipedia thumbnail lookup earlier in the project.

### Health — Exercise Schedule, Doctor Appointments, Food & Nutrition, Body Metrics

One screen (`HealthScreen.tsx`, 4 internal tabs, teal `accentHealth` identity) and one combined `useHealthStore` covering all 4 tables — same combined-store precedent as `useMoneyStore` (savingsEntries/wishlistItems) and `useTimeTableStore` (schedules/slots). Exercises repeat weekly via a comma-separated `daysOfWeek` field (an exercise can span several days at once, e.g. `"1,3,5"` — checked with `.split(',').map(Number).includes(dayOfWeek)`, not a separate row per day like Time Table's `daySchedules`); doctorAppointments are date-specific (`appointmentAt` ISO datetime, upcoming/past computed at render time against `Date.now()`, not a stored status); bodyMetrics is a plain dated weight log with a computed delta against the previous entry. None of the four tables get seed data — health data is personal, left empty on every fresh install (unlike Quotes/News categories).

Food & Nutrition is the AI feature the section was built around: `apps/desktop/electron/ai/food.ts`'s `generateFoodInfo()` follows the exact template `entertainment.ts` established — one JSON-object prompt (`{benefits, caloriesEstimate, considerations}`), regex-extract `{...}` from the raw response, `JSON.parse` with a try/catch falling back to `null` on any failure. Wired the same way as every other AI feature: `food:generateInfo` IPC handler in `main.ts` → `FoodApi` in `packages/core/src/api.ts` → `preload.ts` → `useHealthStore.addFood()`, which creates the row immediately and fills in the AI fields asynchronously once they land (`pendingFoodIds` tracks in-flight rows for the UI's "Getting nutrition info…" state) — identical non-blocking pattern to `useEntertainmentStore.addItem()`. Not grounded in `framework.md`, unlike Entertainment/Earning Ways — nutrition facts aren't a matter of personal values the way "worth your time" or "what to pursue" are. An exercise can also carry an optional `videoUrl`; its thumbnail is fetched via the same `media.fetchYouTubeThumbnail` IPC call Library's videos use.

### Goals & Tasks — tasks live inside a goal, but don't have to

Tasks moved from their own sidebar screen into each Goal's detail dialog (`GoalDetailDialog` in `GoalsScreen.tsx`). `'tasks'` stays out of `TOGGLEABLE_SECTIONS` (there's no standalone screen to toggle) and `TasksScreen.tsx` stays deleted, but `Task.linkedGoalId` is optional again — a task with none is a **"quick task"**: captured before it's clear which goal (if any) it belongs to. `GoalsScreen.tsx` has a permanent "Quick Tasks" section below the goals grid listing every task with no `linkedGoalId`, fully self-contained — same status dropdown, link-open button, edit (pencil), and delete (trash) a goal-level task row has, plus an **Assign** button (`AssignTaskDialog`: pick a goal, optionally one of its milestones) since that's the one action goal-level rows don't need. `openTaskLink()`/`TaskLinkButton` (module-level in `GoalsScreen.tsx`) are shared between this section and goal-level/milestone task rows rather than duplicated per call site.

A task can also nest under one specific milestone via `Task.linkedMilestoneId` (only meaningful alongside a `linkedGoalId`) instead of sitting at goal-level. Milestones in `GoalDetailDialog` are expandable (a chevron per row): the expanded panel shows that milestone's sub-tasks as milestone-style checkboxes (binary done/todo, not the goal-level `todo`/`in-progress`/`done` `Select`), an inline quick-add input, and an **"Assign existing"** button (`AssignExistingTaskDialog`) to pull in any task from elsewhere (a quick task, or one under a different goal/milestone) rather than only ever creating new ones. The same "Assign existing" affordance exists at goal-level (next to "Add task") for pulling a task in without nesting it under any milestone. `useTasksStore.assignTask(id, { linkedGoalId, linkedMilestoneId })` is the thin wrapper every reassignment path calls.

A task can carry one optional link (`Task.linkType`: `'file' | 'folder' | 'url' | 'book' | 'video'`):
- **file/folder**: same `dialog:pickFileOrFolder` + hostname-gating pattern as File Manager (`linkPath`/`linkHostname`; opening only works on the machine that added it).
- **url**: `linkPath` holds the URL, `linkHostname` stays null (not machine-specific), opened via `system.openExternal`.
- **book/video**: `linkTargetId` holds the Book/Video's id, picked from a dropdown of `useBooksStore`/`useVideosStore` data. Linking one calls `updateBook`/`updateVideo` to set that item's new `category` field to the goal's title — Library then shows a "goals"-toned badge on it (see the Library section below; a quick task with no goal skips this tagging, since there's no goal title yet). Clicking the task's link uses `useUiFocusStore` (`packages/core/src/stores/useUiFocusStore.ts`) to set a one-shot `libraryFocus` target and navigates to Library; `LibraryScreen` consumes it in a `useEffect` (switch tab, scroll+highlight the matching card via `document.getElementById('library-book-'+id)`/`'library-video-'+id`, then `clearLibraryFocus()`) so it only fires once per navigation, not on every subsequent Library re-render. **`useTasksStore.removeTask`/`updateTask` clear that badge again** once the task that set it is deleted or relinked elsewhere (checked against every other live task first, since `category` is a single shared value, not a set) — a real gap in the original design, found and fixed after the badge was confirmed to linger past its task's deletion.

`TaskDialog` in `GoalsScreen.tsx` does double duty for add and edit (an optional `task` prop switches it to pre-filled/edit mode, calling `updateTask` instead of `addTask` on submit) — same pattern `SlotDialog` in `TimeTableScreen.tsx` uses for time slots. Its `goal` prop is also optional now, reused as-is for quick-task creation (no goal title in the dialog's own copy, `linkedGoalId` omitted on submit). Goal fields (title/description/category/type/targetDate) are directly editable in `GoalDetailDialog` too, each committing `onUpdate` on blur against local state kept in sync with `goal.id` (not the whole `goal` object, so an in-flight status/progress update from elsewhere doesn't clobber what the user is mid-typing).

**Progress auto-computed from milestones and their sub-tasks**: `useMilestonesStore`'s `addMilestone`/`toggleMilestone`/`removeMilestone`, and `useTasksStore` after any create/status-change/removal/reassignment touching a milestone-linked task, all call `syncGoalProgressForGoal(goalId, milestones)` (exported from `useMilestonesStore.ts`) — once a goal has ≥1 milestone and/or ≥1 milestone-linked task, it computes `completedUnits/totalUnits` (a "unit" is either a milestone or a task nested under one, equal weight) and calls `useGoalsStore.getState().updateGoal(goalId, {progressPct})` directly. This makes `useMilestonesStore` and `useTasksStore` import each other (the former to read live tasks for a goal, the latter to call the sync function after a milestone-linked task changes) — a genuine circular import, kept safe by only ever calling the other side's `getState()`/exported function from inside an async function body, never at module-eval time (confirmed via a clean `electron-vite build` and a dev-mode boot with no runtime error). The progress range input in `GoalDetailDialog` is `disabled` whenever `milestones.length > 0`.

**Auto-fetched goal image**: `useGoalsStore.addGoal` creates the row immediately, then asynchronously calls the existing `media.fetchWikipediaThumbnail(title, '')` (same real-search-never-AI-guessed API Entertainment's posters use, no type hint since goals aren't a fixed enum) and patches `Goal.imageUrl` in if a match lands — same non-blocking enrichment pattern as Entertainment/Food. Shown as a header image on goal cards and atop `GoalDetailDialog`, which also has **Remove image** (`imageUrl: null`) and **Upload image** controls (composes the existing `dialog.pickFileOrFolder('file')` + `system.readFileAsBase64` calls into a `data:` URI client-side — no new IPC). Personal/abstract goal titles ("Save $5000") often won't match anything on Wikipedia — an accepted, honest limitation; manual upload/removal is the mitigation, not a bug to chase further.

### Savings — a personal total + wishlist, not full bookkeeping

`useMoneyStore` was rewritten in place (same hook name, entirely different shape) from accounts/transactions/budgets to `savingsEntries` (amount + `'add' | 'expense'` + date + note) and `wishlistItems` (title, category, estimated cost, status). `computeTotalSavings(entries)` replaces the old `computeAccountBalance` — just the signed sum of every entry. The original `Account`/`Transaction`/`Budget` types and their tables stay defined in `schema.ts`/`shared/src/index.ts` but are **dormant** — nothing in the UI reads/writes them anymore, kept rather than dropped to avoid a destructive migration the user didn't explicitly ask for. The sidebar/Settings label reads "Savings"; the `ToggleableSectionId`/screen id is still `'money'` internally — renaming it would touch Sidebar/SettingsScreen/App routing for no functional gain.

**Wishlist purchases are linked to Savings, not just tracked alongside it.** `WishlistItem.purchaseEntryId` points at the exact `SavingsEntry` created when the item was marked `'done'` (an expense entry for `estimatedCost`, skipped if no cost was ever set — nothing to deduct). `useMoneyStore.setWishlistStatus` orchestrates both tables: → `'done'` creates that entry and links it; leaving `'done'` (back to `'planned'`, or `'cancelled'` — cancelling reverses the deduction too, not just un-planning) removes that exact entry again, so nothing lingers. `editWishlistItem(id, patch)` (backing a new `EditWishlistDialog` in `MoneyScreen.tsx` — there was no wishlist edit UI at all before) also keeps the linked entry's amount in sync if the cost changes on an already-`'done'` item, since the real price is often cheaper/pricier than the estimate.

### Date/time inputs — click anywhere opens the native picker

`packages/ui/src/components/ui/Input` calls `element.showPicker()` on click for `date`/`time`/`datetime-local`/`month`/`week` types, so the whole field is clickable rather than requiring a precise hit on Chromium's small built-in indicator icon. Paired with a `color-scheme: light` / `.dark { color-scheme: dark }` rule in `apps/desktop/src/index.css` (mirrors the same `.dark` class `ThemeProvider` toggles) so the native popup and icon render in a visible palette in dark mode instead of defaulting to a light-only, near-invisible icon. Applies globally — no per-screen wiring needed, since every date/time field in the app already goes through the shared `Input` component.

### Renderer security model

`contextIsolation: true`, `nodeIntegration: false` everywhere. The renderer only ever talks to `window.api` (`packages/core/src/api.ts` defines its shape; `apps/desktop/electron/preload.ts` implements it via `contextBridge`). Any new main-process capability needs three edits: an `ipcMain.handle` in `main.ts`, a matching entry in `preload.ts`'s exposed object, and a type added to the `LifeManagerApi` interface in `api.ts`.

### PDF cover rendering (`packages/ui/src/lib/pdfCover.ts`)

Runs client-side in the renderer via `pdfjs-dist`'s browser build on an offscreen `<canvas>` — deliberately not the Node `canvas` package pdf.js normally wants for server-side rendering, which is itself a native module (same category of risk as `better-sqlite3`, avoided the same way).

### Mobile app (`apps/mobile`) — Capacitor/Android, Phase 1

Not a replica of desktop — a **read-mostly companion** meant for quick glances, sharing the same schema/data (via Drive sync, Phase 2) rather than duplicating desktop's editing UI. Phase 1 (done): scaffold, its own local data layer, a full read-only UI for every module, an editable Library (the one section meant for quick-adding), Time Table local notifications, and local backup (export/import). Phase 2 (not built yet): Android share-intent capture (share a YouTube/web URL or a PDF straight into Library) and mobile-side Drive sync.

**Scope differences from desktop, deliberate**: Dashboard adds a Clock-view Time Table (`TimeTableClock`, reused verbatim from `packages/ui`) alongside the same goals/events/savings/quotes desktop shows. Every other module (Goals, Calendar, Savings, Entertainment, Earning Ways, Jobs, Health, News) is **view-only** — no add/edit, no AI-refresh actions — since mobile never runs its own AI/RSS/job-aggregation calls; it only ever displays whatever the synced DB already has. File Manager doesn't exist on mobile at all (desktop-local-filesystem feature, no equivalent). Library is the one editable section (Books/Videos/Web Links), single-column, touch-sized, built fresh rather than reusing desktop's `LibraryScreen.tsx` (which assumes wide grids and native file-picker dialogs).

**Data layer**: `packages/db/src/capacitorDriver.ts` implements `DataStore` (see above) using `@capacitor-community/sqlite`'s native SQLite binding, running the exact same `SCHEMA_STATEMENTS` and the same `ensureColumn` ad hoc migration approach as desktop — this is what lets the two apps' `.sqlite` files be interchangeable once Drive sync lands. Secret settings (API keys, OAuth tokens) use `packages/db/src/secretCryptoWeb.ts` — a Web Crypto (`crypto.subtle`) AES-256-GCM implementation producing the byte-identical `enc:<iv>:<tag>:<data>` format as desktop's Node-`crypto`-based `secretCrypto.ts`, using the *same* raw 32-byte key (precomputed once via `scryptSync` and hardcoded, since Web Crypto has no built-in scrypt) — verified round-trip both directions (Web-encrypted → Node-decrypted and vice versa) before wiring it in, since this is exactly the kind of thing that silently breaks a future Drive-synced settings row otherwise.

**`window.api` on mobile** (`apps/mobile/src/api/mobileApi.ts`) implements the full `LifeManagerApi` shape in the same JS context as the UI (no separate main process to delegate to) — `db`/`settings` call into the Capacitor SQLite driver; `system.openExternal`/`openWebsite` use `@capacitor/browser`; `media.*` (YouTube oEmbed, Wikipedia lookup, `fetchWebPreview`'s og:image scraping) are the same regex/fetch logic as `apps/desktop/electron/main.ts`, just running client-side; `backup.exportDatabase`/`importDatabase` are real (see below). Everything else desktop-only (native file dialogs, AI provider calls, News/Jobs refresh, Drive sync) is a deliberate stub returning a clear "not available on mobile" result — never omitted from the type, so the contract stays honest.

**Why `fetch()` works here without hitting CORS**: a WebView's `fetch()` would normally be subject to browser CORS restrictions that don't apply to Electron's Node main process — arbitrary third-party pages/APIs don't set CORS headers for a `capacitor://localhost` origin. Fixed via `capacitor.config.ts`'s `plugins.CapacitorHttp.enabled: true`, which patches `fetch`/`XMLHttpRequest` to route through native networking instead of the WebView's own network stack, sidestepping CORS entirely.

**Status bar overlap** (`apps/mobile/src/layout/MobileShell.tsx`): the WebView draws edge-to-edge by default, so unstyled content collides with the system status bar — confirmed live (the Dashboard's date/greeting rendered underneath the clock/battery icons). The JS-side fix (`@capacitor/status-bar`'s `StatusBar.setOverlaysWebView({ overlay: false })`, called once in `main.tsx`) turned out **not** to be enough by itself — confirmed live it still overlapped after adding it, almost certainly Android's enforced edge-to-edge on newer API levels ignoring the legacy overlay flag. The fix that actually worked: CSS `padding-top: max(1.5rem, env(safe-area-inset-top))` on the scrollable content wrapper (mirrors the bottom tab bar's existing `pb-[env(safe-area-inset-bottom)]`) — `index.html`'s `viewport-fit=cover` meta tag makes the real inset available to `env()`. Kept the JS call too (harmless, and helps on older/non-edge-to-edge Android versions) rather than relying on either one alone.

**Time Table local notifications** (`apps/mobile/src/notifications/timeTableNotifications.ts`, `@capacitor/local-notifications`): one recurring notification per `TimeSlot`, firing weekly at its `startTime` via `schedule.on: { weekday, hour, minute }` — a genuine recurring trigger, not a one-off `at` time. `Weekday.Sunday = 1` in the plugin's own enum, so `dayOfWeek + 1` (this app's `dayOfWeek` is 0=Sunday, per `DAY_NAMES`) maps directly. Every notification this feature schedules carries `extra: { source: 'timeTable' }` so cancel/reschedule (via `getPending()` filtered by that tag) only ever touches its own notifications. Notification ids are a deterministic djb2-style hash of the slot's UUID (Android ids are 32-bit ints) so re-scheduling replaces rather than duplicates. Toggle lives in `MobileSettingsScreen.tsx`, persisted as a plain `settings.get/set` key (`mobileTimeTableNotifications`, 'on'/'off') like any other setting; `App.tsx` re-runs the schedule once on boot if it was already on, keeping notifications in sync across restarts. Since Time Table isn't editable on mobile and nothing syncs yet (Phase 2), this only has real slots to schedule once Drive sync brings desktop's Time Table data over — verified live that the permission prompt, grant, and settings toggle all work correctly even with zero slots.

**Local backup / import-export** (`packages/db/src/capacitorDriver.ts`'s `exportToJson`/`importFromJson`, wired into the existing `BackupApi`): a **different format from desktop's** — a full JSON dump (`@capacitor-community/sqlite`'s own `exportToJson('full')`/`importFromJson`) rather than desktop's raw binary `.sqlite` file, since there's no reliable way to get the native plugin's internal database file path. Two real API-shape gotchas hit and fixed by checking the installed package's own `.d.ts` rather than trusting docs/search summaries (a doc summary said `importFromJson` took a parsed object and lived on the same class as `exportToJson` — both wrong): `db.exportToJson(mode)` (returning `{ export: JsonSQLite }`) lives on the **`SQLiteDBConnection` instance**, while `sqlite.importFromJson(jsonString)` (a JSON **string**, not the parsed object) lives on the **top-level `SQLiteConnection` manager** — different classes for the two halves of the same round-trip. Export writes the JSON to `Directory.Cache` via `@capacitor/filesystem` then hands it to `@capacitor/share`'s native Share sheet (no "Save As" dialog concept on Android — the user picks where it actually goes: Drive, Files, email). Import uses a plain HTML `<input type="file" accept="application/json">` — a Capacitor WebView is real Chromium, so this already opens the native document picker with no extra plugin — reads it with `FileReader`, sanity-checks the parsed JSON has a `tables` array before trusting it (same "verify before trusting" discipline as desktop's SQLite-header check), then `window.location.reload()`s (mobile's equivalent of desktop's `app.relaunch()`) so every store reflects the freshly-imported data. Live-verified as a genuine overwrite, not a no-op: added a throwaway Web Link, imported an earlier export that predated it, confirmed the app reloaded and the throwaway row was gone.

**First-time setup / local environment gotchas** (all confirmed live getting Phase 1 running in the `Pixel_9` AVD, none are code bugs):
- `npm install` at the repo root covers `apps/mobile` too (same npm workspaces). `npx cap add android` (run once, from `apps/mobile/`) generates the native `android/` project — not hand-written, regenerate rather than hand-edit if it ever needs to be recreated.
- **Gradle's own JDK may not trust `services.gradle.org`/`dl.google.com`'s certificate chain**, failing with `PKIX path building failed` even though `curl`/npm work fine for the same hosts — a stale bundled JDK `cacerts` trust store (either the Android Studio JBR or a separate installed JDK), unrelated to network access itself. Fix that worked: run Gradle with `-Djavax.net.ssl.trustStoreType=Windows-ROOT` (via `$env:GRADLE_OPTS` in PowerShell), which delegates TLS trust decisions to the Windows OS certificate store instead of the JDK's own bundled one.
- **The Android emulator's own baked-in system CA bundle can be similarly stale**, independent of the Gradle/JDK issue above — confirmed live via `adb logcat` showing `SSLHandshakeException`/`Trust anchor for certification path not found` for the *exact same* real HTTPS requests (`fetchWebPreview` fetching a real article page) that `curl` succeeds at instantly. This is a per-AVD-system-image snapshot going stale over time, not a code defect — a real device's normal, regularly-updated OS trust store won't have this problem. The Play Store AVD images (`Pixel_9`/`Pixel_8a` here) aren't rootable (`adb root` → "cannot run as root in production builds"), so there's no quick fix from the host machine; this was accepted as a known dev-sandbox limitation rather than chased further, since the app's own code degrades gracefully on a failed fetch either way (confirmed: add-web-link still completes, just without a fetched preview, exactly the same fallback behavior a real offline device would see).
- Live-verified end-to-end in the emulator (screenshots via `adb exec-out screencap`, taps via `adb shell input tap`): schema creation + all `ensureColumn` migrations, seed data insertion, every read-only screen rendering real data, the Dashboard Clock view, the full Library add → row-appears-immediately → (attempted) preview fetch → delete (hardRemove) cycle, the status bar fix, the notification permission prompt + on/off toggle, and a real export → mutate → import → reload → mutation-undone round trip (inspected the exported JSON directly via `adb shell run-as <pkg> cat cache/...`, pushed it back in via `adb push` + the OS document picker).

## Non-obvious state

- No test suite exists yet.
- `npm run dist` produces a real Windows installer (NSIS `.exe`) via `electron-builder` — see the Packaging section below. `npm run build` alone still only produces the unpacked `out/` folder.
- Git repo is initialized with regular commits — commit after each noticeable change, per the user's standing instruction.
- AI features live in `apps/desktop/electron/ai/`, not a `packages/ai` workspace package as structure.md originally sketched — main-process-only code (network calls, `framework.md` file access), so it never needed to be a shared package; nothing in `packages/ai` exists.
- Google Drive sync is code-complete but inert without the user's own Google Cloud OAuth credentials pasted into Settings — can't be exercised end-to-end without that.
- `apps/mobile` is Phase 1 only (see the Mobile app section above): boots, has its own local SQLite, full read-only UI, an editable Library, Time Table local notifications, and local JSON backup — but no share-intent capture and no Drive sync yet (mobile's data doesn't sync anywhere yet, it's a standalone local DB). Both are explicitly scoped as Phase 2, not forgotten.
- AI calls (especially Gemini's default "thinking" mode) can take 15–40+ seconds. Not a bug; noted here so a slow response isn't mistaken for a hang.
- **Recurring gotcha, width**: `Select`/`Input`'s base class in `FormControls.tsx` hardcodes `w-full`. A call site passing `w-auto` (or any other width utility) to squeeze it into a tight inline row (a status dropdown next to a title, a filter next to a heading) can silently lose that fight — Tailwind's generated CSS resolves by class *generation* order, not by className string order, so which one wins isn't guaranteed by writing the override "after" the base class. Confirmed to actually break things twice now (a currency `Input`, then five separate inline `Select`s across Goals/Money/Library/Entertainment/Earning Ways) — the fix each time was wrapping the control in its own explicitly-sized `<div>` (e.g. `<div className="w-28 shrink-0">`) rather than trying to out-specificity the base class inline. Do this preemptively for any new inline/auto-width `Input`/`Select` rather than waiting for it to visibly cut off text.
- **Recurring gotcha, height**: the same base class also hardcodes `py-2` (16px of vertical padding). Overriding just the height (`h-7`/`h-8`, i.e. 28px/32px) for a compact inline `Select` — without also overriding `py-2` — leaves too little room for `py-2` + the text's line-height combined, so the option text renders vertically clipped (looks like the top/bottom of the letters are cut off) rather than centered. This bit the same five inline `Select`s a second time, after the width fix — and the *first* attempted fix (plain `py-1 text-xs` added to the className) didn't actually work either, still visibly clipped. Root cause, confirmed by inspecting the real built CSS (`npm run build`, then grep the output `.css` for both rules): Tailwind emits utilities of the same CSS property in ascending scale order (`.py-1 { ... }` appears in the stylesheet *before* `.py-2 { ... }`), and with equal specificity the *later* rule in the stylesheet wins — so `py-2` (scale value 2 > 1) always wins over a plain `py-1` override, full stop, regardless of which one is written later in the className string. This is the general form of the width gotcha above, just for padding instead of width, and it means a wrapping `<div>` doesn't help here (padding is intrinsic to the control's own box). The fix that's actually verified working: Tailwind's `!` important prefix on every conflicting utility — `className="h-7 !py-1 !text-xs"` (confirmed via the built CSS: `.\!py-1 { padding-top/bottom: 0.25rem !important }`, which is guaranteed to beat a plain, non-important `.py-2` regardless of stylesheet order). When in doubt about whether a plain override "took," inspect the actual generated CSS rather than trusting source order or scale intuition — both have been wrong here before.
